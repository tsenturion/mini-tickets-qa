# Мини-заявки — стенд для курса тестирования

Минимальное готовое приложение для курса ручного и автоматизированного тестирования: два экрана, две роли, заявки и комментарии. Проверяйте интерфейс, REST API и PostgreSQL, проектируйте тесты и разбирайте ошибки по логам. Разрабатывать новые функции приложения для прохождения курса не нужно.

Стек: Vue 3 + Vite + Tailwind, FastAPI, PostgreSQL и Docker. В репозитории шесть вариантов: три способа развёртывания, каждый с исправленной версией и с учебными дефектами.

## Установка и самопроверка

Зависимости компьютера: Git, PowerShell 7 (`pwsh`), Python 3.13, Node.js 22 LTS с npm, Docker Desktop с Linux-контейнерами и Docker Compose. Python 3.14 не является проверенной заменой 3.13. Отдельно устанавливать PostgreSQL не требуется: база запускается в Docker. Postman нужен для ручных API-упражнений; JDK 21 или 25 — только для Windows-агента Jenkins.

Клонируйте **все ветки**, без `--depth` и `--single-branch`. Для приватного GitHub сначала авторизуйтесь в GitHub Desktop или Git Credential Manager:

```powershell
$taskProjects = Join-Path $env:USERPROFILE 'repos'
New-Item -ItemType Directory -Path $taskProjects -Force | Out-Null
git clone https://github.com/tsenturion/mini-tickets-qa.git "$taskProjects/testing"
Set-Location "$taskProjects/testing"
git switch monolith/fixed
.\scripts\Prepare-Lab.ps1 -Grader
docker compose up -d --wait
.\.venv\Scripts\python.exe scripts/verify_grader.py --full
```

`Prepare-Lab.ps1 -Grader` создаёт изолированную `.venv`, устанавливает Python/npm-зависимости, собирает приложение и контейнер оценщика. Первый запуск скачивает большой образ браузеров. `verify_grader.py --full` проверяет исправленные варианты, все 24 одиночных включения дефектов и отклонение постоянно падающей и пустой работ. Успех всей самопроверки — код выхода `0`; отчёты находятся в `artifacts/grader-self-test`.

Для локальных контрольных UI-тестов дополнительно установите браузеры и проверьте текущую ветку:

```powershell
.\scripts\Prepare-Lab.ps1 -Browsers
.\.venv\Scripts\python.exe ci/verify.py
```

Для занятий с GitLab и Jenkins отдельно запустите:

```powershell
.\scripts\Prepare-LocalCI.ps1
.\scripts\Prepare-LocalCI.ps1 -JenkinsPlugins
```

Первая команда скачивает несколько ГБ и запускает контроллеры. Вторая добавляет нужные плагины Jenkins и перезапускает только его; не выполняйте её во время заданий. Можно сразу использовать вторую команду вместо двух. Первичная настройка, регистрация runner и запуск Windows-исполнителей описаны в [инструкции локальных CI](docs/ЛОКАЛЬНЫЕ-CI.md). Для всей среды с GitLab выделите Docker ориентировочно 12 ГБ памяти и дополнительное место под образы. Для обычных UI/API/SQL-занятий GitLab и Jenkins не нужны.

Все три скрипта находятся в `scripts` **в каждой из шести продуктовых веток**. Версии пакетов закреплены в `requirements.lock`, `requirements-test.lock` и `frontend/package-lock.json`. Образы PostgreSQL, приложения и оценщика создаются независимо от системных Python-пакетов и установленной на компьютере базы данных.

После первичной настройки GitLab/Jenkins зарегистрируйте runner и подключите исполнители. Runner работает в отдельном окне PowerShell, которое нужно оставить открытым на время проверки:

```powershell
$taskCIRoot = Join-Path (Get-Location) '.runtime/gl'
.\.runtime\ci-tools\gitlab-runner.exe register --config .runtime/ci-tools/config.toml --url http://localhost:8929 --executor shell --shell pwsh --builds-dir "$taskCIRoot/builds" --cache-dir "$taskCIRoot/cache"
.\.runtime\ci-tools\gitlab-runner.exe run --config .runtime/ci-tools/config.toml
```

Токен регистрации GitLab получите в настройках runner с меткой `qa-docker`. В Jenkins заранее создайте узел `qa-windows` с меткой `qa-docker`, одним executor и рабочим каталогом `.runtime/jenkins` внутри проекта (в интерфейсе укажите полный путь, например `C:\Users\user\repos\testing\.runtime\jenkins`). Сам проект размещайте в коротком пути без кириллицы: это важно для служебных bat-файлов Git-плагина и bind mount Docker Desktop. После смены пути переподключите исполнитель.

В другом PowerShell скачайте небольшой `agent.jar` и подключите Jenkins. Секрет узла сохраните в локальном `.runtime/ci-tools/jenkins-agent.secret` по инструкции [первичного подключения](docs/ЛОКАЛЬНЫЕ-CI.md); не помещайте его в Git. Параметры кодировки предотвращают искажение кириллицы в выводе Java:

```powershell
New-Item -ItemType Directory -Path .runtime/ci-tools -Force | Out-Null
Invoke-WebRequest http://localhost:8085/jnlpJars/agent.jar -OutFile .runtime/ci-tools/agent.jar
[Console]::OutputEncoding = [Text.UTF8Encoding]::new()
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' -jar .runtime/ci-tools/agent.jar -url http://localhost:8085/ -secret '@.runtime/ci-tools/jenkins-agent.secret' -name qa-windows -webSocket -workDir .runtime/jenkins
```

После `Connected` оставьте окно открытым. Журналы исполнителя находятся в `.runtime/jenkins/remoting`, логи заданий и отчёты — в Jenkins с 30-дневным сроком хранения. Секреты и локальные журналы не входят в Git.

## Быстрый запуск

Нужен Docker с Linux-контейнерами и Docker Compose. Откройте PowerShell в каталоге проекта:

```powershell
docker compose up -d --build --wait
```

Приложение: http://localhost:8000. Swagger: http://localhost:8000/docs. Контракт: `contract/openapi.json`. PostgreSQL: `localhost:55432`, база/пользователь `lab`, учебный пароль `lab-local-only`. Эти данные относятся только к создаваемой среде Docker и не заменяют настройки установленной на компьютере PostgreSQL.

Учётные записи: `anna@example.test`, `boris@example.test`, `operator@example.test`. Учебный пароль всех трёх — `LabPassword1!`. Роль оператора есть только у третьей записи. Доступна самостоятельная регистрация.

Все порты опубликованы только на loopback. Реальные персональные данные и рабочие пароли в стенд не загружать.

| Архитектура | Исправленная | Учебные дефекты |
|---|---|---|
| Общая сборка Vue + FastAPI | `monolith/fixed` | `monolith/buggy` |
| Отдельный Vue/Nginx + FastAPI | `client-server/fixed` | `client-server/buggy` |
| Пользователи + заявки, две БД | `microservices/fixed` | `microservices/buggy` |

Проверьте `variant.json`, чтобы определить текущий вариант. В `buggy` по умолчанию активны все восемь дефектов. Для одного дефекта перед запуском установите `$env:LAB_DEFECTS='D01'` и пересоберите среду. UI-дефекты выбираются при сборке frontend. В исправленных ветках переключателей дефектов в исполняемом коде нет.

Для одновременных архитектур используйте разные Git worktree и `LAB_PROJECT`, `LAB_PORT`, `LAB_DB_PORT`. Перед переключением архитектуры останавливайте её Compose-проект; не подключайте микросервисы к тому же тому БД, что монолит.

.\.venv\Scripts\python ci/verify.py

Создание отдельного репозитория работ с четырьмя студенческими ветками:

```powershell
.\scripts\New-StudentRepo.ps1
.\scripts\Start-Student.ps1 -Student 1
```

Пишите и коммитьте тесты в созданном `student-work`, не изменяя продукт. Оценщик запускает только сохранённый Git-коммит работы:

```powershell
.\.venv\Scripts\python scripts/freeze_release.py
.\.venv\Scripts\python grader/run.py --submission student-work --refs artifacts/release-lock.json
```

Для итоговой матрицы добавьте `--full`. Для индивидуальных заданий используйте `--defects D01,D02,D07`. Результаты: `artifacts/grading/grade.md` и `grade.json`; код выхода `0` — зачёт, `1` — работа не прошла, `2` — ошибка среды. Качество структуры и обоснованность тестов преподаватель проверяет отдельно.

Выпуск закреплён в `releases/1.0.0.json`, который хранится в Git и переносится при клонировании. По умолчанию оценщик и `freeze_release.py` используют эти шесть точных коммитов, даже если ветки позже изменятся. Для подготовки следующего выпуска преподаватель может получить вершины веток через `freeze_release.py --current` и отдельно утвердить новый манифест.

Для каждого запуска оценщик создаёт отдельную сеть, временные тома и непривилегированный контейнер тестов. Работе доступны HTTP-вход и каталог её артефактов; Docker socket, секреты CI, БД и рабочий каталог преподавателя не подключаются. Исходники эталонов открыты, поэтому это учебное оценивание, не система защиты экзамена от намеренного обхода.

Логи приложения находятся в постоянном томе, сохраняются между перезапусками, ротируются и очищаются по возрасту 30 дней. Экспорт: `docker compose cp app:/app/logs ./artifacts/server-logs`; для микросервисов используйте `identity` и `tickets`. Не используйте `down --volumes` для обычной остановки: это удаляет тома среды. CI удаляет только собственные временные ресурсы после сохранения отчётов.

## 1. Границы продукта и технологии

Тестируйте готовое приложение, а не разрабатывайте его. Здесь нет платежей,
почты, внешних интеграций, каталога товаров и сложного администрирования:
два экрана, две роли и 12 REST-операций дают достаточно материала для всего курса.

Vue 3 + Vite + Tailwind отвечают за UI, FastAPI — за HTTP и бизнес-правила,
SQLAlchemy + psycopg — за PostgreSQL, Alembic — за миграции. Для тестов:
Pytest + Requests, Playwright, Postman и Locust; для отчётов — JUnit, JSON и Allure.
Приложение в Docker использует Python 3.13, оценщик — Python закреплённого образа
Playwright. Наличие Python 3.14 на хосте само по себе не доказывает совместимость
нативного инструментария; для воспроизводимой подготовки используйте Python 3.13.

## 3. Что именно сравнивают три архитектуры

«Клиент-сервер» и «монолит» не являются взаимоисключающими архитектурами:
браузер обращается к серверу во всех вариантах. Здесь это учебные названия
трёх способов поставки, позволяющие сравнить процессы, сеть, отказы и диагностику.

В монолите Vue поставляется вместе с FastAPI. Во втором варианте Vue/Nginx
развёртывается отдельно от FastAPI. В третьем — отдельные сервисы пользователей
и заявок, отдельные базы и роли. Один процесс PostgreSQL выбран ради экономии
ресурсов; брокер сообщений, распределённые транзакции и Kubernetes не требуются.

В микросервисах базы/роли `identity` и `tickets`, учебные пароли
`identity-local-only` и `tickets-local-only`. Роли не подключаются к чужой БД.
Обычного межбазового JOIN нет: проверяйте взаимодействие через API.

## 4. Организация занятий для четырёх человек

Каждому достаточно собственной ветки тестов и независимой среды, а не отдельного
приложения с иной предметной областью. Номера студентов 1–4 дают HTTP-порты
8101–8104 и PostgreSQL-порты 55441–55444. Имена Compose-проектов разделяют тома и сети.

`Start-Student.ps1` берёт архитектуру текущей продуктовой ветки. Переменные
`LAB_*` остаются в текущем PowerShell: команда остановки в этом окне относится
к запущенной среде. При смене архитектуры используйте другой проект/том.

Роли «аналитик требований», «автор тестов», «исследователь», «ревьюер» можно менять
между занятиями. В конце — перекрёстное ревью PR/MR. Каждый должен уметь объяснить
собственные проверки, а не только получить зелёный pipeline.

## 6. Требование — источник ожидаемого результата

Идентификаторы `AUTH-*`, `TICKET-*`, `COMMENT-*`, `UI-*` связывают требования,
ручные кейсы, баг-репорты, маркеры pytest и отчёт оценщика. Текущий ответ buggy
не является эталоном: он намеренно неверен. Не меняйте ожидание теста под дефект.

При противоречии сначала оформите замечание: что неоднозначно, на какое решение
это влияет, какой вопрос нужно уточнить. Семь принципов тестирования обсуждаются
на практике: найденные дефекты не доказывают полноту, полный перебор невозможен,
один и тот же smoke не заменяет новое исследование.

## 7. Классы эквивалентности и граничные значения

Заголовок после обрезки пробелов — 3–80 Unicode code points. Начните с 2/3/80/81,
добавьте пустую строку, пробелы, emoji и комбинируемые символы. Комментарий после
обрезки — 1–300; пароль без обрезки — 8–64. Приоритет — `low`, `normal`, `high`.

Различайте отсутствие поля, `null`, пустую строку и неизвестное поле JSON.
После 422 проверьте не только код, но и отсутствие созданной/изменённой записи.
HTML maxlength считает UTF-16 иначе, чем Python: формы намеренно не обрезают строку,
сервер применяет единое правило. В OpenAPI ограничение после trim описано отдельно.

## 8. Таблицы решений, состояния и Pairwise

Для таблицы решений комбинируйте роль, авторство, состояние и действие.
Пользователь видит свои заявки, оператор — все, но не может редактировать
заголовок или удалять чужую заявку. Автор меняет/удаляет только свою `new`.
Недоступный объект — 404, недостаточная роль — 403, недопустимое состояние — 409.
Точные правила и приоритеты проверок — в [требованиях](docs/ТРЕБОВАНИЯ.md).

Разрешены `new → active`, `active → closed`, `closed → active`;
повтор текущего состояния допустим. Статус меняет только оператор.
Проверяйте запрещённые переходы, повтор запроса и сохранение результата.
Скрытая кнопка не защищает API: повторяйте действия прямыми HTTP-запросами.

Pairwise подходит для сочетаний браузера, роли и приоритета, но не заменяет
обязательные границы, критичные проверки доступа и переходы небольшой машины состояний.

## 9. Ручное и исследовательское тестирование

Короткий smoke: вход → создание → открытие → комментарий → выход.
Регрессия добавляет негативные сценарии, права, состояния, фильтр и сохранение.
Для исследовательской сессии задайте цель, например «найти рассинхронизацию
карточки и списка после ошибок сети», ограничьте время, записывайте гипотезы.

Результат сессии — не только баги: полезны проверенные риски, неопределённости,
непроверенные области и следующий эксперимент. Хаотичные клики не заменяют регрессию,
а успешный маршрут не позволяет сделать вывод о всей системе.

## 10. Тестовая документация и метрики

[Шаблоны](docs/ШАБЛОНЫ.md) помогают оформить объём, риски, окружение и критерии завершения.
Кейс содержит предусловия, данные, действия и наблюдаемый результат.
Баг-репорт — SHA/ветку, среду, шаги, факт, ожидание, severity/priority,
вложения и `X-Request-ID`, если дефект связан с запросом.

В отчёте разделяйте «пройдено», «провалено», «не запускалось» и «заблокировано средой».
Покрытие требований = требования с выполненными проверками / требования в согласованном объёме.
Количество тестов не равно покрытию. Для плотности дефектов явно определяйте
знаменатель; сравнение архитектур по числу заранее внедрённых ошибок малоинформативно.
Высокий mutation score не доказывает отсутствие других дефектов.

## 11. Ручное API и Postman

Импортируйте `postman/mini-tickets.collection.json` и `postman/local.environment.json`,
измените `base_url` на свою среду. Коллекция показывает регистрацию, токен и цепочки
действий, но не является полной матрицей требований.

Расследование: запрос/заголовки → код/JSON → повторное чтение → при необходимости
SQL → серверный лог с тем же request_id. Для 204 проверяйте пустое тело, не вызывайте
JSON-декодирование. Для 401 различайте отсутствующий, неверный, истёкший и отозванный токены.
Не ограничивайтесь статусом 200 — проверяйте содержимое и отсутствие лишних данных.

Bearer здесь — непрозрачная серверная сессия, не JWT и не OAuth 2.0.
Basic Auth/OAuth изучаются отдельно; их реализация не добавлена ради числа технологий.

## 12. DevTools и отладка

В Network сопоставьте действие с методом, путём, телом, ответом и временем.
В Console ищите ошибки JavaScript. Затем выясните, изменились ли API и БД.
Если PATCH сохранил новое значение, а строка списка старая, исследуйте UI,
а не меняйте PostgreSQL. Перезагрузка страницы может скрыть такой дефект.

Charles/Fiddler допустимы на собственной учебной среде. Не направляйте через
учебный перехватчик рабочие пароли и трафик других пользователей.

## 13. PostgreSQL: что проверить после POST

Сохраните UUID ответа POST и читайте именно эту запись, не «последнюю строку»:

```sql
-- Подставьте UUID заявки, созданной вашим тестом.
SELECT id, title, priority, status, author_id
FROM tickets WHERE id = '00000000-0000-0000-0000-000000000001';
```

Сопоставьте поля с запросом и серверными значениями: автор, `new`, UTC-время.
Повторно прочитайте объект через API. Ответ HTTP, строка БД и последующее чтение
проверяют разные границы и могут дать разные наблюдения.

`sql/01_registration.sql` показывает INSERT/ROLLBACK: повторите с COMMIT и вторым
соединением. `02_checks.sql` содержит JOIN, группировку и поиск сирот.
`03_mutation_cleanup.sql` меняет только известную запись упражнения.
`04_microservices.sql` не имитирует несуществующий межбазовый JOIN.

## 14. Подготовка и очистка данных

Уникальные email и UUID делают тесты независимыми. Не изменяйте общие seed-записи
и не используйте DELETE без WHERE. Для UI/API создавайте данные через публичные
операции; в SQL-практикуме можно использовать прямые скрипты личной БД.

Транзакция одного SQL-соединения не откатит POST, выполненный приложением в другом.
Фикстура очищает доступные ей объекты; полностью среду сбрасывает запускатель,
создавший временные тома. Заявки после жизненного цикла нельзя просто удалить
от имени пользователя — ограничение продукта не следует обходить в переносимом UI-тесте.

## 15. Выбор сценариев автоматизации

Начните с повторяемых, важных и однозначных правил. Комбинации входных данных
дешевле проверять через API; браузер нужен для отображения, взаимодействия и интеграции.
Unit проверяет правило изолированно, SQL — данные, API — контракт, UI — наблюдение пользователя.

Не переводите каждый ручной шаг в медленный браузерный тест. Исследование удобства
и спорных требований полезно оставить ручным. Тесты модуля 8 проверяют публичный
HTTP/UI-контракт: прямого подключения к БД в контейнере оценщика нет.

## 16. Pytest, fixtures, параметризация и Page Object

`student-template` содержит стартовую структуру, но не решение.
Фикстура готовит уникальные данные и доступную очистку; разные browser context
разделяют сессии пользователей. Параметры представляют выбранные классы/границы,
а не случайные сотни строк. Не рассчитывайте на порядок тестов и фиксированные ID.

Page Object объединяет действия с экраном; тест сохраняет бизнес-ожидание.
Предпочитайте `get_by_role`, `get_by_label` и точечные `data-testid`.
Проверяйте конкретную строку заявки, не первое совпадение на странице.
Используйте ожидания Playwright и `expect`, а не фиксированный sleep.
Автоожидание клика не доказывает завершение асинхронного сохранения.

Каждый тест имеет `@pytest.mark.api` или `@pytest.mark.ui` и
`@pytest.mark.requirement('TICKET-01')` с подходящим требованием.
Маркер не заменяет содержательный assert/expect.

В заготовке и оценщике используется `--import-mode=importlib`: одноимённые файлы
API/UI не конфликтуют. Не пытайтесь лечить ошибку import file mismatch удалением
кеша на каждом запуске — сначала проверьте режим импорта и структуру модулей.

## 17. Выборочные локальные проверки

.\.venv\Scripts\python.exe scripts/check_documentation.py
$env:BASE_URL = 'http://localhost:8101'
.\.venv\Scripts\python.exe scripts/check.py quality/api quality/ui --screenshot=only-on-failure --tracing=retain-on-failure

Прямой запуск контрольных дефектных тестов на buggy будет красным — это ожидаемо.

## 18. Алгоритм оценщика и защита от ложного зачёта

Сначала одни и те же тесты проходят три исправленные архитектуры, затем монолит
в обратном порядке. После этого каждый назначенный дефект включается отдельно.
По умолчанию мутанты проверяются на монолите; `--full` проверяет их на всех архитектурах.
Порог по умолчанию — 75% назначенных дефектов.

Засчитывается AssertionError в фазе выполнения теста с подходящим требованием
при подтверждённом контрольным тестом мутанте. Для D07/D08 требуется UI-тест.
Skip, ошибка фикстуры, пустая работа, постоянное падение и изменение состава тестов
не заменяют обнаружение дефекта. Эталон должен пройти полностью.

Код 0 означает зачёт; 1 — незачтённую/неверную работу; 2 — проблему инфраструктуры.
Преподаватель отдельно оценивает тест-дизайн, читаемость, независимость и аргументацию.
Оценщик запускает только коммит, не незакоммиченные изменения.

## 19. Самопроверка оценивания и эксплуатации

```powershell
.\.venv\Scripts\python.exe scripts/verify_grader.py --full
.\.venv\Scripts\python.exe scripts/verify_operations.py
```

Первая команда создаёт правильную, постоянно падающую и пустую работы.
Хорошая проходит четыре эталонных прогона и обнаруживает 24 одиночных включения
(8 дефектов × 3 архитектуры); две плохие отклоняются уже на эталоне.
Артефакты — `artifacts/grader-self-test`. Нужен заранее собранный образ оценщика.

Вторая проверяет изоляцию четырёх сред, сохранность после рестарта и отказ identity.
`verify_matrix.py --architecture monolith` — отдельная диагностическая матрица
доверенных контрольных тестов с локальным браузером; она не заменяет контейнерную приёмку.

## 20. Закреплённые коммиты и ограничения изоляции

Манифест выпуска закрепляет продукт, а отчёт — ещё и SHA работы/оценщика.
`freeze_release.py --current` получает кандидатов для следующего выпуска:
их сначала проверяют, затем отдельно утверждают. Все шесть коммитов должны быть в клоне.

Временные каталоги `.runtime/runs` наследуют разрешения рабочей папки Windows,
чтобы Docker Desktop мог прочитать bind mount. Глобальные ACL Windows Temp не меняются.
Коды Docker 125/126/127 означают ошибку запуска контейнера, не дефект студенческого теста.

Это не защищённый экзамен: исходники открыты, демонстрационный workflow изменяем.
Для произвольного недоверенного кода нужны отдельный одноразовый агент/VM и дополнительная изоляция.

## 21. Приватный GitHub и реальные PR

Продуктовый workflow запускается на push, PR и вручную. Студенческий —
из `student-template/.github/workflows/qa.yml`. Для него нужны Actions variables
`QA_PRODUCT_REPOSITORY`, `QA_PRODUCT_REF` (доверенный SHA) и secret
`QA_PRODUCT_SSH_KEY` — отдельный read-only deploy key продукта, не персональный токен.

Проверяется SHA исходной ветки PR, не предполагаемый merge commit.
Для курса используйте ветки общего приватного репозитория: обычные PR из fork
не получают этот secret. Не используйте pull_request_target для выполнения
непроверенного кода с привилегиями. Наличие workflow ещё не означает успешный CI:
проверьте его по [критериям приёмки](docs/ПРОВЕРКА.md).

## 22. Локальные GitLab и Jenkins

Большие образы загружает владелец:

```powershell
.\scripts\Prepare-LocalCI.ps1
```

Контроллеры работают в Docker: GitLab — [localhost:8929](http://localhost:8929),
Jenkins — [localhost:8085](http://localhost:8085).
Начальные пароли, runner и агент: [ЛОКАЛЬНЫЕ-CI](docs/ЛОКАЛЬНЫЕ-CI.md).
Не публикуйте пароли и токены в Git, отчётах или переписке.

Агенты с меткой `qa-docker` работают на Windows-хосте Docker: bind mount видит
настоящие пути, а контроллерам не требуется Docker socket.
`ci/bootstrap.py` создаёт собственную venv постоянного агента.
На Linux системные библиотеки Chromium устанавливает администратор заранее.

Настоящий MR требует runner, прав клонирования, credentials и отправки исходной ветки.
Зеркало GitHub само по себе не создаёт MR. Для сравнения систем используйте одинаковый source SHA.

## 23. Доверенный Jenkins и граница CI/CD

`Jenkinsfile` проверяет продукт, `ci/grading.Jenkinsfile` оценивает работу
по Git-адресу и SHA. Второй файл берётся из доверенного коммита преподавателя.
Красные JUnit мутантов не должны переопределять успешный итоговый код оценщика.
Защита ветки и обязательный статус настраиваются на площадке, не одним YAML.

Реализован CI: сборка, временное развёртывание, проверки, отчёты и очистка.
Автоматического CD на общую учебную машину нет: выбранный выпуск переносит преподаватель,
чтобы pipeline не менял среду посреди занятия. Детали — в [CI](docs/CI.md).

## 24. Логи, артефакты и расследование падения

Порядок: `grade.json` → конкретный сценарий → `runner.log`/`infrastructure.log`
→ `compose.log`/JSON-логи → trace/скриншот → проверяемое требование.
При Access is denied на bind mount сначала проверяют среду, а не меняют assert.
После изменения образа оценщика его пересобирают через Prepare-Lab.ps1 -Grader.

Логи содержат run_id, request_id, событие и время. Пароли и исходные тексты исключений
с SQL-параметрами не записываются. Приложение дописывает журналы между запусками,
ротирует ежедневно и очищает по возрасту 30 дней.

CI-артефакты хранятся 30 дней. В GitLab отключите бессрочное хранение последнего
успешного pipeline, в Jenkins — «хранить навсегда». Локальную очистку выполняет
`clean_artifacts.py` при проверках; на выключенной машине она произойдёт при следующем запуске.
Allure-данные формируются автоматически, HTML требует отдельного CLI/плагина.

## 25. Нагрузка и стресс-тестирование

`load/locustfile.py` — сценарий упражнения, не готовый SLA.
Установите отдельные `load/requirements.txt`, запускайте только на своей среде,
начните с малого числа пользователей. Сравнивайте p50/p95, долю ошибок,
пропускную способность, CPU/память и логи, фиксируйте профиль и ресурсы машины.

Ноль запросов не является успехом. Короткий smoke нагрузки не измеряет предел
производительности. Для стресса заранее определите условие остановки и постепенно
увеличивайте нагрузку; не выполняйте его на общей среде других студентов.

## 26. Безопасность, совместимость и удобство

Проверяйте доступ к чужим UUID, серверную роль, неизвестные поля, отзыв сессии
и вывод HTML как текста. SQL-подобные строки проверяйте как данные, не выполняйте
разрушительные команды. Набор упражнений не является полным аудитом OWASP Top 10.

Chromium — основной автоматический браузер; Firefox/WebKit, узкий экран, масштаб,
клавиатура и фокус — дополнительные матрицы. Установка браузера не равна успешному прогону.
WebKit не доказывает совместимость со всеми Safari, эмуляция ширины не заменяет
настоящее устройство. Мобильного приложения нет, Appium здесь не нужен.

## 27. Остановка, перенос и сохранность

```powershell
docker compose stop
docker compose start
```

Тома сохраняются. `down` без `--volumes` удаляет контейнеры/сеть, но не БД.
`down --volumes` удаляет данные и историю журналов — это не обычная остановка.
Проверки очищают только собственные временные проекты после экспорта доказательств.

Для переноса клонируйте продукт с доступом ко всем веткам и отдельно работы,
подготовьте зависимости и повторите самопроверку. Не переносите .venv, .runtime,
токены или каталоги Docker между машинами. См. [эксплуатацию](docs/ЭКСПЛУАТАЦИЯ.md).

## 28. Поддержка учебных пояснений

Авторский Python снабжён русскими docstring, сложные места — комментариями о причинах.
JS/Vue используют JSDoc, PowerShell — встроенную справку. Проверка
`scripts/check_documentation.py` предотвращает пропуски, но не оценивает качество текста.

После изменения общего кода синхронизируйте шесть веток и выполните
`scripts/audit_branches.py`. API-контракт обновляется через
`scripts/export_contract.py` из fixed, не buggy. Кеши, локальные настройки,
секреты и генерируемые отчёты исключены из Git.
