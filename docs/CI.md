# Подключение CI на учебном стенде

Проект содержит два типа pipeline: проверка текущего варианта продукта и оценивание тестов студентов. Все команды работают локально. Удалённые серверы автоматически не настраиваются.

## Продуктовые ветки

`python ci/verify.py` запускает временную среду текущей архитектуры, проверяет API/UI/БД и сохраняет артефакты. Для buggy восемь ожидаемых падений проверяются отдельно; они не делают продуктовый pipeline красным, если дефекты подтверждены.

GitHub Actions использует `.github/workflows/qa.yml`. GitLab использует `.gitlab-ci.yml`; зарегистрируйте shell-runner с тегом `qa-docker`, Python и доступом к Docker. На Linux предварительно установите системные зависимости браузера командой Playwright `install --with-deps chromium`; Windows-runner устанавливает обычный Chromium. Jenkins использует `Jenkinsfile` и агент с меткой `qa-docker`.

Для Jenkins Multibranch установите Git, Pipeline и соответствующий GitHub/GitLab Branch Source plugin, укажите репозиторий, включите обнаружение веток и PR/MR. Webhook либо периодическое сканирование инициирует сборку. На локальном GitLab откройте обычный MR: просто зеркало GitHub не создаёт MR автоматически.

## Оценивание работы

Рекомендуемый вариант для локального учебного стенда: преподавательское задание Jenkins из `ci/grading.Jenkinsfile`. Источник этого Jenkinsfile — доверенный закреплённый коммит продукта. Параметры: адрес репозитория работы, точный SHA исходной ветки PR/MR, полная или быстрая матрица. Коммит студента извлекается в отдельную временную папку через `git archive`; вложенные незакоммиченные каталоги, `.git` и секреты рабочего каталога туда не попадают.

Образ `mini-tickets-grader:1.0` подготовьте заранее через `Prepare-Lab.ps1 -Grader`. Код запускается непривилегированно, без Docker socket и секретов. Сеть студенческого контейнера соединена только с HTTP-входом приложения. БД и внутренние сервисы остаются в отдельной сети.

Альтернатива — самостоятельные демонстрационные pipelines репозитория работ, заготовки находятся в `student-template`. С ними проще изучать YAML, но их код доступен для изменения вместе с тестами. Поэтому автоматический окончательный зачёт/обязательный статус должен приходить из доверенного преподавательского задания, с настройкой защиты ветки на площадке. Наличие файла CI само по себе не защищает правила оценки.

Для GitHub задайте variables `QA_PRODUCT_REPOSITORY` и `QA_PRODUCT_REF`. Для GitLab — `QA_PRODUCT_URL`, `QA_PRODUCT_REF`. Укажите реальный SHA доверенного выпуска, а не изменяемую ветку. При копировании шаблона на другой GitLab-host используйте URL, доступный агенту. Пароли и токены задаются только в настройках credentials/variables, не в исходниках.

GitHub проверяет `pull_request.head.sha`; GitLab MR по умолчанию проверяет source commit. В Jenkins при сравнении трёх систем выберите тот же SHA. Проверка результата слияния, если нужна, является отдельным прогоном.

## Результаты и хранение

Для приватного GitHub-продукта в репозитории работ дополнительно создайте secret
`QA_PRODUCT_SSH_KEY` с отдельным read-only deploy key продукта. Не используйте
персональный токен с правами записи. Ветки PR должны принадлежать этому учебному
репозиторию; fork-PR не получает secret. Проверка студенческого workflow является
демонстрацией интеграции, не заменой доверенного итогового задания.

Постоянные GitLab/Jenkins-агенты используют `ci/bootstrap.py`: зависимости ставятся
в собственную `.runtime/ci-venv`, а не глобальный Python. На Linux системные библиотеки
Chromium должны быть установлены администратором заранее. Локальные контроллеры,
runner и агент описаны в [ЛОКАЛЬНЫЕ-CI](ЛОКАЛЬНЫЕ-CI.md).

`grade.json` содержит обнаруженные дефекты, процент, статус и точные коммиты продукта/студента/оценщика. `grade.md` — краткий человекочитаемый результат. Для каждого прогона сохраняются JUnit, Allure-данные, browser trace, скриншоты при падении, консоль и логи приложения.

JUnit дефектных прогонов может быть красным при успешном итоговом оценивании: ожидаемые падения означают обнаруженные дефекты. При обязательном статусе PR/MR используйте именно итоговый код оценщика. Коды: 0 — зачёт; 1 — не зачтено/неверная работа; 2 — среда не позволила проверить работу.

Для Allure можно открыть результаты локальным CLI (`allure serve <каталог-allure>`) или настроить Jenkins Allure plugin. Генерация HTML-отчёта — дополнительный шаг после установки CLI; JUnit и JSON доступны без него.

GitHub: retention-days 30. GitLab: expire_in 30 days; отключите сохранение артефактов последнего успешного pipeline сверх срока. Jenkins: logRotator на 30 дней; убедитесь, что сборки не помечены «хранить навсегда». Локальные отчёты — `artifacts`, вне Git.

## Приёмка после переноса

1. Запустите исправленную и дефектную ветки в каждой системе.
2. Проверьте работу с правильными тестами, работу с постоянным падением и запуск при недоступной среде.
3. Убедитесь, что различаются «найден дефект», «работа не прошла» и «среда недоступна».
4. Откройте настоящий PR/MR, измените тест и проверьте повторный запуск на новом SHA.
5. Проверьте артефакты и срок их хранения. Полученные результаты фиксируйте отдельно от проверки синтаксиса конфигураций.
