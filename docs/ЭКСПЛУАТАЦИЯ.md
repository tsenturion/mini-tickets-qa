# Запуск и перенос на учебный стенд

## Перенос через Git

Публикацию выполняет владелец. После добавления своего remote отправьте все шесть веток (`git push origin --all`) и при необходимости теги. На стенде клонируйте репозиторий, выберите нужную ветку и выполните `docker compose up -d --build --wait`.

Git clone обычно создаёт одну локальную ветку и остальные `origin/*`. `git switch --track origin/client-server/fixed` создаст нужную локальную ветку. Для оценивания `scripts/freeze_release.py` умеет фиксировать и локальные ветки, и `origin/*`.

Код рассчитан на Python 3.13+; Docker фиксирует свою Python-среду и не зависит от установленной на стенде версии 3.14. Если тесты запускаются непосредственно в Python 3.14, установите зависимости в отдельную виртуальную среду и выполните `scripts/check.py quality/unit`; локальный прогон на версии 3.14 следует подтвердить на том компьютере.

Наличие Node.js, Python и PostgreSQL не означает наличие Docker. Проверьте `docker version` и `docker compose version`; на Windows нужны Linux-контейнеры и работающий Docker Desktop/WSL2. Если Docker отсутствует, установите его отдельно до подготовки курса. Файлы проекта не изменяют системную PostgreSQL, Jenkins и GitLab.

## Четыре среды

`Start-Student.ps1 -Student 1` … `4` создаёт проекты `mini-student-1` … `4`, HTTP-порты 8101–8104 и PostgreSQL-порты 55441–55444. Данные и логи разделены томами. Запускайте только те архитектуры, которые нужны для текущего занятия.

Для микросервисов подключайтесь к PostgreSQL-контейнеру на опубликованном порту: база/пользователь `identity`, учебный пароль `identity-local-only`; база/пользователь `tickets`, учебный пароль `tickets-local-only`. Суперпользователь Docker остаётся только у преподавателя. Владелец `identity` не имеет доступа к базе `tickets`, и наоборот.

Обычная остановка: `docker compose stop`; повторный запуск: `docker compose start`. `docker compose down` удаляет контейнеры и сеть, сохраняя тома. Для сброса данных создайте новый `LAB_PROJECT` либо адресно удалите только том БД остановленного учебного проекта после проверки имени. Не удаляйте том логов.

## Диагностика

1. В Network найдите запрос, HTTP-код и `X-Request-ID`.
2. Экспортируйте логи через `docker compose cp app:/app/logs ./artifacts/server-logs`; в микросервисах — из `identity` и `tickets`.
3. Найдите этот идентификатор в JSON-логах. Для микросервисов он передаётся при внутренней проверке сессии.
4. Сопоставьте запись БД и ответ API. Не определяйте причину только по сообщению UI.
5. Если проблема при старте, проверьте `docker compose ps` и `docker compose logs`; убедитесь, что миграции завершились.

Логи приложения сохраняются в томах; очистка файлов старше 30 дней выполняется при запуске и каждый час работающего сервиса. Строки исключений и тела запросов с паролями/токенами не сохраняются. Не помещайте секреты в названия тестов, тестовые строки или вложения: отчёты тестировщика могут содержать проверяемые значения.

Временные среды `ci/verify.py` и `grader/run.py` сохраняют копии логов перед удалением только своих ресурсов. Их очистка не затрагивает учебные среды. Каталог `artifacts` на рабочей машине регулярно очищайте по сроку хранения курса; в CI настройте 30-дневное хранение.

## Проверки отказа и повторного запуска

На микросервисном стенде выполните `docker compose stop identity`, отправьте защищённый запрос к заявкам: ожидается `503`, запись запроса должна появиться в логах tickets. После `docker compose start identity` запрос с действующим токеном снова проходит. Перезапуск одного сервиса не должен удалить заявки или сессии.

Для проверки БД выполните SQL из каталога `sql`. Учебный пароль реальной системной PostgreSQL и данные удалённого рабочего стола не нужны для этих команд и не хранятся в проекте.
