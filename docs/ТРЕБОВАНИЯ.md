# Контракт версии 1.0.0

Требования одинаковы для всех шести веток. Ошибка учебной версии не меняет контракт.

## Пользователи

| Код | Правило |
|---|---|
| AUTH-01 | Email обрезается по краям, переводится в нижний регистр, должен содержать одну `@` и точку после неё, без пробелов. Максимум 254 символа входной строки. Уникальность нормализованного значения. Пароль 8–64 символа, без обрезки. Регистрация только с ролью `user`; неизвестные поля запрещены. Повторный email — `409`. |
| AUTH-02 | Вход выдаёт случайный Bearer-токен на 3600 секунд. Неверный пароль, неизвестный пользователь, неверный/истёкший/отозванный/отсутствующий токен — `401`. Выход отзывает текущую сессию. Другие сессии сохраняются. Пароль и хеши отсутствуют в ответах. |
| AUTH-03 | Пользователь видит только свои заявки; оператор — все. Просмотр чужой недоступной заявки, комментариев и действия над ней возвращают `404`. Оператор не получает право редактировать заголовки и удалять чужие заявки. |

## Заявки и комментарии

| Код | Правило |
|---|---|
| TICKET-01 | Заголовок после обрезки пробелов: 3–80 Unicode code points. Границы 2/3/80/81. Комбинируемые символы считаются отдельно. |
| TICKET-02 | Приоритет `low`, `normal`, `high`; по умолчанию `normal`. Неизвестное значение — `422`, без создания/изменения записи. |
| TICKET-03 | Автор задаётся сервером. Начальный статус `new`. Автор меняет заголовок/приоритет и удаляет только собственную новую заявку; недопустимое состояние — `409`. Чужая доступная оператору заявка — `403` при редактировании/удалении. Удаление каскадно удаляет комментарии. Пустой PATCH, явный null и неизвестные поля — `422`. |
| TICKET-04 | Только оператор меняет статус. Разрешены `new→active`, `active→closed`, `closed→active`; повтор текущего статуса допустим. Остальные переходы — `409`, недостаточная роль — `403`. |
| TICKET-05 | Фильтр `status` возвращает только указанный статус. Неизвестное значение — `422`. Список ограничен правами и сортируется по `created_at DESC, id DESC`. |
| COMMENT-01 | Комментарий сохраняет фактического автора, идентификатор заявки, текст и UTC-время. Текст после обрезки: 1–300 code points. Добавление к `closed` — `409`. Чтение доступно тому, кому доступна заявка. Порядок `created_at ASC, id ASC`. |
| UI-01 | Доступны вход, регистрация, список и работа с заявкой внутри второго экрана. Результат операции или ошибка видны пользователю. Поля имеют подписи и доступны с клавиатуры. |
| UI-02 | После изменения приоритета актуальное значение видно в списке без перезагрузки страницы. |
| UI-03 | Заголовки и комментарии отображаются текстом: HTML не интерпретируется, скрипты не выполняются. |

Матрица ролей и переходов проверяется также через прямые запросы, независимо от доступности кнопок в интерфейсе. Длины пароля, заголовка и комментария считаются в Unicode code points. Формы передают введённую строку без обрезания браузерным maxlength; сервер выполняет нормализацию и валидацию. В OpenAPI верхняя граница после обрезки указана описанием и расширением `x-maxLength-after-trim`, а не ограничением длины исходной строки.

## API

Полный машиночитаемый контракт: `contract/openapi.json`. Корень — `/api`.

| Метод | Путь | Успех |
|---|---|---|
| POST | `/auth/register` | 201, `{id,email,role}` |
| POST | `/auth/login` | 200, `{access_token,token_type,expires_in}` |
| POST | `/auth/logout` | 204, пустое тело |
| GET | `/auth/me` | 200, пользователь |
| GET | `/tickets` | 200, массив заявок |
| POST | `/tickets` | 201, заявка |
| GET | `/tickets/{id}` | 200, заявка |
| PATCH | `/tickets/{id}` | 200, заявка |
| DELETE | `/tickets/{id}` | 204, пустое тело |
| PUT | `/tickets/{id}/status` | 200, заявка |
| GET | `/tickets/{id}/comments` | 200, массив комментариев |
| POST | `/tickets/{id}/comments` | 201, комментарий |

Идентификаторы — UUID, даты — ISO 8601 с UTC-смещением. Ошибка: `{"error":{"message":"…","request_id":"…"}}`; при валидации добавляется `fields` с путём поля и сообщением, без исходного значения. На каждом ответе — `X-Request-ID`; допустимый переданный идентификатор сохраняется.

При недоступной БД — `503`. В микросервисах недоступность сервиса пользователей приводит к `503` на защищённом API заявок, а не к обходу прав. Детали внутренних исключений в HTTP-ответ не передаются.

## Данные

Единая БД содержит `users`, `sessions`, `tickets`, `comments` с PK/FK, уникальным email, ограничениями ролей/статусов/приоритетов и индексами авторов, статусов и связей комментариев. Длина заголовка проверяется приложением: это позволяет отдельно исследовать границы ответственности API и БД.

Микросервисы: база `identity` содержит пользователей/сессии; `tickets` — заявки/комментарии. Межбазовых FK и обычных JOIN нет; роли БД не могут подключаться к чужой базе. Один процесс PostgreSQL выбран для экономии ресурсов, сервисы остаются отдельно развёртываемыми.
