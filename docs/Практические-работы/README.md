# Практические работы

Программа состоит из 15 последовательных практических работ по одному приложению
«Мини-заявки». Каждая следующая работа использует понятия и материалы предыдущих
практик. Опубликованы все пятнадцать работ обновлённой программы курса.

## Как устроена программа

- работа № 1 знакомит с архитектурами приложения;
- работа № 2 вводит CI/CD и личный репозиторий тестов;
- работы № 3–7 охватывают тест-дизайн, документацию, функциональные и
  нефункциональные проверки;
- работы № 8–9 посвящены API и отладке;
- работы № 10–11 посвящены PostgreSQL и тестовым данным;
- работа № 12 связывает ручные API-проверки, отладку и базовую автоматизацию;
- работа № 13 развивает UI-автоматизацию на Playwright;
- работа № 14 переносит созданные тесты в GitHub Actions, GitLab CI и Jenkins;
- работа № 15 объединяет созданные проверки в межархитектурный регрессионный
  прогон.

Основой практик служат учебные учётные записи и тестовые данные. Репозиторий
тестов развивается последовательно, а продуктовые ветки используются как объект
изучения и тестирования. Конкретная ветка продукта, порядок подготовки среды и
способ самопроверки указываются внутри соответствующей работы.

[Карта покрытия программы](ПОКРЫТИЕ-ПРОГРАММЫ.md) показывает связь всех тем с
работами, использование шести продуктовых веток и единый цикл PR/MR и CI.

## Общий цикл результата

Когда работа создаёт или меняет файлы личного репозитория, сохраните их в
рабочей ветке, отправьте один SHA в GitHub и GitLab и откройте PR/MR в `main`.
Для запущенных GitHub Actions и GitLab CI сопоставьте событие, job, фактическую
команду, итог, первую значимую ошибку и опубликованные артефакты. После
исправления проверяется уже новый SHA на обеих площадках. Если файловых
изменений нет, пустой коммит и формальный PR/MR не добавляют информации.

Первичный импорт, два remote и перенос результата после merge выполняйте по
[инструкции синхронизации GitHub и GitLab](../СИНХРОНИЗАЦИЯ-GITHUB-GITLAB.md).
Для одного изменения выбирайте одну площадку, на которой выполняется merge, а
затем переносите получившийся `main` на вторую площадку.

Jenkins запускается в работах, где он указан в шагах. Результаты pipeline
используются для самопроверки, а не как отдельная процедура оценивания.
