# Карточки преподавателя

Исходные дефекты доступны для изучения; перед самостоятельной работой студент ориентируется на требования. Исправленная ветка каждой архитектуры является эталоном.

| Код | Требование | Воспроизведение | Ошибка | Контроль |
|---|---|---|---|---|
| D01 | TICKET-01 | POST с заголовком из 81 символа | 201 вместо 422 | `test_d01_title_81` |
| D02 | TICKET-02 | POST с приоритетом `urgent` | Создание с `normal` вместо отказа | `test_d02_unknown_priority` |
| D03 | AUTH-03 | Пользователь B получает по ID заявку A | Доступ вместо 404 | `test_d03_other_owner` |
| D04 | TICKET-04 | Оператор переводит новую заявку сразу в closed | Успех вместо 409 | `test_d04_forbidden_transition` |
| D05 | TICKET-05 | Создать свою новую и активную заявки, запросить new | Возвращаются обе | `test_d05_status_filter` |
| D06 | COMMENT-01 | Оператор комментирует заявку пользователя | Автором становится владелец заявки | `test_d06_comment_author` |
| D07 | UI-02 | Автор меняет приоритет в карточке | В списке старое значение | `test_d07_priority_refresh` |
| D08 | UI-03 | Комментарий `<b>пример</b>` | Разметка исполняется вместо отображения текста | `test_d08_comment_is_plain_text` |

Для ручной практики `LAB_DEFECTS=all`; для измерения обнаружения каждый дефект включается отдельно на свежей среде. При UI-дефекте необходима пересборка frontend. На исправленной ветке переменная не меняет поведение.

Сначала контроль готовности и контрольный тест преподавателя, затем интерпретация результата. Ошибки сбора тестов, setup/teardown, пропуски и недоступность приложения не считаются найденными дефектами. Для D07/D08 требуется падающая проверка UI; для остальных — проверка соответствующего требования.

Нагрузочная деградация и отключение сервиса пользователей — отдельные исследовательские упражнения, не входят в восемь детерминированных дефектов.
