# Личный репозиторий тестов «Мини-заявок»

Здесь находятся ваши API/UI-тесты на Python + Pytest + Requests + Playwright и готовые файлы CI. Приложение, PostgreSQL, шесть продуктовых веток и оценщик остаются в основном репозитории `mini-tickets-qa`. Два стартовых примера проверяют запуск, но ещё не подтверждают обнаружение учебных дефектов.

Рабочая схема: создайте личный репозиторий из заготовки, опубликуйте `main`, настройте CI, добавьте тесты в отдельной ветке и откройте PR/MR **в `main` своего репозитория**. Форк продукта и общий репозиторий работ для этого не нужны. Можно выбрать GitHub или GitLab; оба сразу нужны только для сравнения CI. Jenkins может проверить тот же коммит из любого из них.

## 1. Создайте репозиторий из заготовки

Если вы уже читаете этот README в созданном личном репозитории, переходите к разделу 2.

Нужны Git и PowerShell 7. Откройте PowerShell в клонированном основном проекте. Если продукт ещё не скачан, выполните:

```powershell
$taskProduct = Join-Path $env:USERPROFILE 'repos/testing'
git clone https://github.com/tsenturion/mini-tickets-qa.git "$taskProduct"
Set-Location -LiteralPath $taskProduct
git switch monolith/fixed
```

Не клонируйте поверх существующего каталога. Если проект уже есть, достаточно перейти в его корень. Не используйте `--depth` или `--single-branch`.

Если Git ещё не настроен на вашем компьютере, задайте свои имя и адрес для коммитов:

```powershell
git config --global user.name 'Ваше имя'
git config --global user.email 'ваш-адрес@example.org'
```

Создайте работу в новом каталоге. Вместо `my-testing-work` можно выбрать собственное имя:

```powershell
$taskTests = Join-Path $env:USERPROFILE 'repos/my-testing-work'
.\scripts\New-StudentRepo.ps1 -Destination "$taskTests"
Set-Location -LiteralPath $taskTests
git status
git branch --show-current
```

Результат — самостоятельный Git-репозиторий, первый коммит и ветка `main`, без удалённых адресов. Существующий каталог скрипт не перезаписывает. Альтернатива: `-Destination student-work` создаёт каталог внутри продукта; относительный путь всегда отсчитывается от корня продукта, а не от текущего окна PowerShell.

Генератор копирует **содержимое** `student-template`, а не саму папку:

| В основном проекте | В личном репозитории |
|---|---|
| `student-template/.github/workflows/qa.yml` | `.github/workflows/qa.yml` — GitHub Actions |
| `student-template/.gitlab-ci.yml` | `.gitlab-ci.yml` — GitLab CI |
| `student-template/ci_grade.py` | `ci_grade.py` — запуск оценивания из GitLab |
| `student-template/tests/`, `student-template/pages/`, `student-template/conftest.py` | `tests/`, `pages/`, `conftest.py` — ваши тесты и фикстуры |
| `student-template/requirements.txt`, `student-template/pytest.ini`, `student-template/.gitignore`, `student-template/README.md` | Файлы зависимостей, настройки и эта инструкция в корне |
| `ci/grading.Jenkinsfile` | **Не копируется**: доверенное задание Jenkins остаётся в продукте |

Проверьте скрытые файлы командой `git ls-files`. В пути CI не должно остаться префикса `student-template/`. Не копируйте корневые CI-файлы продукта: они проверяют приложение, а не вашу работу. Секреты, `.env`, виртуальная среда, исходники приложения и оценщик в работу не переносятся.

## 2. Установите зависимости и запустите примеры

Нужен Python 3.13. Все команды ниже выполняются **в корне личного репозитория**. Активация виртуальной среды не требуется:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
```

Последняя команда скачивает браузер. Git, Python и браузер достаточны для написания тестов, если приложение уже запущено. Node.js, отдельная PostgreSQL и контроллеры CI в репозитории тестов не нужны. Для самостоятельного запуска приложения используйте установку в README продукта: Docker Desktop с Linux-контейнерами, `Prepare-Lab.ps1` и Docker Compose. Одна среда продукта может обслуживать несколько последовательных запусков тестов.

Чтобы запустить приложение самостоятельно, перейдите в корень **продукта** и выберите уникальный положительный номер среды. Например, команда `.\scripts\Start-Student.ps1 -Student 7` создаст отдельный Compose-проект с HTTP-портом 8107 и PostgreSQL-портом 55447. При конфликте задайте `-HttpPort` и `-DbPort` явно. Затем из личного репозитория выполните:

```powershell
$env:BASE_URL = 'http://localhost:8107'
.\.venv\Scripts\python.exe -m pytest --junitxml=artifacts/results.xml --alluredir=artifacts/allure --screenshot=only-on-failure --tracing=retain-on-failure
```

`localhost` относится к компьютеру, где выполняются тесты. Если приложение запущено на другой машине, используйте выданный адрес вместо `localhost`.

Оба стартовых примера должны пройти на исправленном работающем приложении. В CI оценщик сам создаёт временные приложения: переменную `BASE_URL` там настраивать не нужно. Не публикуйте `artifacts`, `.venv` или секреты — они уже исключены через `.gitignore`.

## 3. Опубликуйте начальную ветку

В своём GitHub создайте **пустой** репозиторий, например `mini-tickets-tests`: без автоматического README, лицензии и `.gitignore`. Замените `YOUR_LOGIN` своим логином:

```powershell
git remote add origin https://github.com/YOUR_LOGIN/mini-tickets-tests.git
git push -u origin main
```

Для GitLab вместо GitHub используйте адрес своего пустого проекта, скопированный из кнопки Clone. Например, для локального GitLab:

```powershell
git remote add origin http://localhost:8929/YOUR_LOGIN/mini-tickets-tests.git
git push -u origin main
```

Выполните только один из этих вариантов: `origin` добавляется один раз. Проверьте `git remote -v` и убедитесь, что `main` стала основной веткой на площадке.

## 4. Настройте GitHub Actions

В **своём репозитории тестов** разрешите Actions в `Settings → Actions → General`. Затем в `Settings → Secrets and variables → Actions → Variables` добавьте:

| Переменная | Значение |
|---|---|
| `QA_PRODUCT_REPOSITORY` | `tsenturion/mini-tickets-qa` либо выданный преподавателем `владелец/репозиторий`, без URL |
| `QA_PRODUCT_REF` | Полный SHA доверенного коммита продукта: 40 шестнадцатеричных символов, не имя ветки и не коммит вашей работы |

Получите SHA у преподавателя. Его можно прочитать командой `git rev-parse HEAD` в утверждённой копии продукта. Для сравнения площадок нужен одинаковый утверждённый коммит, доступный на каждой из них. Версии всех шести вариантов берутся из `releases/1.0.0.json` этого коммита; CI сохраняет разрешённые SHA в `release-lock.json`.

Переменные Actions не копируются при `git clone` или `git push`; их нужно создать в каждой работе. Создавайте рабочую ветку в своём репозитории и направляйте PR в его `main`.

После открытия PR workflow `Проверка работы` запустится автоматически; следующие коммиты в ту же ветку запустят его снова. Обычный push без открытого PR в этой заготовке **не запускает** проверку. Ручная альтернатива — `Actions → Проверка работы → Run workflow`. Для неё файл workflow должен быть опубликован в основной ветке, поэтому сначала нужен push `main`. [Условия ручного запуска GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

## 5. Настройте GitLab CI, если используете GitLab

Для сравнения с GitHub можно отправить **тот же репозиторий и те же коммиты** на второй сервер. Сначала создайте свой пустой проект GitLab, затем:

```powershell
git remote add gitlab http://localhost:8929/YOUR_LOGIN/mini-tickets-tests.git
git push gitlab main
```

Если `origin` уже указывает на GitLab, второй адрес не нужен. Для внешнего сервера используйте его реальный HTTPS-адрес; `localhost:8929` работает только на компьютере, где запущен локальный GitLab.

В **проекте тестов**, `Settings → CI/CD → Variables`, задайте:

| Переменная | Значение |
|---|---|
| `QA_PRODUCT_URL` | HTTPS Clone URL продукта на **том же GitLab**; для локального стенда — `http://localhost:8929/root/mini-tickets-qa.git` |
| `QA_PRODUCT_REF` | Полный SHA утверждённого коммита продукта, как для GitHub |

Это не секреты. Выберите область `All`, отключите `Protected` для этих двух переменных, чтобы они были доступны в обычной рабочей ветке MR. Не помещайте пароль или токен в URL. Адаптер использует автоматически выдаваемый `CI_JOB_TOKEN`, а не личный токен администратора. Адрес сервера должен совпадать с `CI_SERVER_URL`, включая имя хоста и порт; удалённый HTTP запрещён, исключение — локальный loopback.

Если политика GitLab ограничивает межпроектный `CI_JOB_TOKEN`, попросите преподавателя добавить **ваш проект тестов** в `Settings → CI/CD → Job token permissions → CI/CD job token allowlist` **проекта продукта**. Не отключайте ограничение для всех проектов. [Правила доступа GitLab job token](https://docs.gitlab.com/ci/jobs/ci_job_token/).

В `Settings → CI/CD → Runners` должен быть доступен работающий runner с тегом `qa-docker`, Git, Python 3.13 и доступом к Docker. Его подготавливает преподаватель по `docs/ЛОКАЛЬНЫЕ-CI.md` продукта. Shell-runner выполняет YAML с правами своего пользователя: к общему runner подключайте только согласованные учебные проекты и проверяйте изменения CI до запуска. Для несогласованного кода используйте доверенное задание Jenkins, описанное ниже.

Отключите сохранение артефактов последнего успешного pipeline сверх срока (`Keep artifacts from most recent successful jobs`): в YAML срок уже задан как 30 дней. После открытия MR внутри своего проекта pipeline запускается автоматически; последующие push в его исходную ветку запускают новые проверки. Без MR обычный push не запускает pipeline. Для ручной проверки используйте `Build → Pipelines → New pipeline` и выберите ветку. Не включайте merged results pipelines для сравнения с GitHub: сравнивается точный исходный SHA работы, а не результат слияния.

## 6. Напишите тесты и откройте PR/MR

Из корня личного репозитория создайте свою ветку:

```powershell
git switch -c tests/module-8
```

Добавьте тесты в `tests/api` и `tests/ui`, Page Object — в `pages`, общие фикстуры — в `conftest.py`. Используйте `docs/ТРЕБОВАНИЯ.md` и актуальное задание из `docs/Практические-работы/README.md` **репозитория продукта**. У каждого теста укажите `@pytest.mark.api` или `@pytest.mark.ui` и соответствующий идентификатор, например `@pytest.mark.requirement('TICKET-01')`.

Не используйте прямой доступ к БД в переносимых API/UI-тестах модуля 8. Создавайте уникальные данные, удаляйте новые заявки в завершающей части фикстуры, не меняйте общие исходные записи. Аккаунты и заявки, прошедшие жизненный цикл, окончательно удаляет запускатель временной среды.

Исправленные версии должны проходить полностью. Пропуски, постоянные падения, ошибки настройки и тесты без проверок мешают достоверной самопроверке. Полезный комплект включает API и UI, отрицательные сценарии, осмысленную параметризацию и Page Object. Ориентир — пять API- и два UI-теста; важнее покрытые требования, чем количество строк.

После локального запуска сохраните и отправьте изменения:

```powershell
git add tests pages conftest.py
git commit -m 'Добавлены проверки требований модуля 8'
git push -u origin tests/module-8
git rev-parse HEAD
```

Если нужен и второй сервер, выполните также `git push gitlab tests/module-8`. На GitHub откройте `Pull requests → New pull request`: base — `main`, compare — `tests/module-8` **вашего репозитория**. На GitLab откройте `Merge requests → New merge request`: source — `tests/module-8`, target — `main` вашего проекта. Добавьте описание сценариев, требований и локального результата. При сравнении CI убедитесь, что в обоих запросах один SHA.

Не направляйте этот PR/MR в `mini-tickets-qa`: корневой CI продукта проверяет приложение, а не вашу работу. Изменения для исправления замечаний отправляйте новыми коммитами в ту же ветку. Незакоммиченные изменения и локальный запуск не обновляют оценку PR/MR.

## 7. Выполните полную проверку Jenkins

Корневой `Jenkinsfile` в личной работе не нужен. Файл `ci/grading.Jenkinsfile` берётся из доверенного коммита **продукта**, поэтому ссылка на Pipeline остаётся независимой от рабочей ветки. Для запуска подготовьте URL PR/MR и полный SHA команды `git rev-parse HEAD`; коммит должен быть отправлен на сервер.

Задание типа Pipeline настраивается через `Pipeline script from SCM → Git`: адрес и credentials продукта, закреплённый SHA, `Script Path = ci/grading.Jenkinsfile`. Нужен исполнитель с меткой `qa-docker`, Git, Python и Docker. Для локального подключения используйте `docs/ЛОКАЛЬНЫЕ-CI.md` продукта. В `Build with Parameters` указываются:

| Параметр | Значение |
|---|---|
| `SUBMISSION_URL` | Clone URL вашего репозитория тестов |
| `SUBMISSION_SHA` | Точный исходный коммит вашего PR/MR |
| `SUBMISSION_CREDENTIALS_ID` | ID Jenkins credentials для checkout работы; оставьте пустым, если они не требуются |
| `FULL_MATRIX` | Включить для проверки всех дефектов на всех трёх архитектурах |

Секреты продукта и работы — разные credentials с минимальными правами чтения. В параметр передаётся ID credentials, а не сам пароль. Доступ к изменению задания и выбору credentials остаётся у администратора Jenkins.

В этой заготовке Jenkins запускается **по параметрам**: автоматический webhook и публикация его статуса в PR/MR не настроены. Автозапуск на PR/MR предоставляют GitHub/GitLab выше. Jenkins позволяет независимо повторить проверку того же исходного SHA и сопоставить журналы и артефакты трёх систем.

## 8. Прочитайте результат

В GitHub скачайте артефакт `grading`, в GitLab — артефакты задания `grade`. Итог: `product/artifacts/grading/grade.json` и `grade.md` (в скачанном архиве GitHub верхний путь может быть сокращён). В Jenkins откройте артефакты сборки: `product/artifacts/grading-НОМЕР_СБОРКИ/`. Там же находятся журналы, JUnit, Allure-данные, трассировки браузера и скриншоты падений; срок хранения — 30 дней.

Код оценщика `0` означает успешную полную проверку, `1` — несоответствие тестового комплекта условиям проверки, `2` — ошибку среды. Падения тестов на специально дефектных версиях ожидаемы; ориентируйтесь на итоговые `grade.json`/`grade.md`, а не на отдельный красный JUnit. Стартовая заготовка может быть зелёной локально и красной в полной матрице: два примера ещё не обнаруживают дефекты. Сначала прочитайте журнал и отделите ошибку среды от результата теста.

Если CI не запустился, проверьте расположение файлов в корне, наличие открытого PR/MR и разрешение Actions/доступный runner. Если не скачивается продукт — переменные, точный SHA и права чтения. Ошибка конфигурации или недоступный Docker — не доказательство дефекта приложения.

Файлы CI в вашей работе можно изменять, поэтому они демонстрируют интеграцию. Доверенное задание Jenkins даёт независимую полную матрицу. Ссылки на PR/MR, исходный SHA и результат проверки добавьте в собственный итоговый отчёт; общий репозиторий чужих работ для этого не требуется.
