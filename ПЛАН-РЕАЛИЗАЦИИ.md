# План реализации минимального стенда для курса тестирования

Статус: локальная реализация выполнена; фактические проверки и границы приёмки описаны в [журнале проверки](docs/ПРОВЕРКА.md). Внешние CI и большой образ оценщика подготавливаются отдельно.
Дата: 6 сентября 2026 года.
Группа: четыре студента.
Подтверждённый стек: Vite, Vue 3, FastAPI, Tailwind CSS, PostgreSQL, Docker.
Обязательные результаты: шесть постоянных веток приложения, поддержка GitHub Actions, GitLab CI и Jenkins, автоматическая проверка студенческих тестов при PR/MR.

## 1. Назначение и ограничение объёма

Учебный продукт — «Мини-заявки»: пользователь создаёт заявку, оператор меняет её статус, участники оставляют комментарии. Приложение предоставляет достаточно наблюдаемого поведения для тестирования интерфейса, API, данных, прав доступа и переходов состояний.

Основная работа при реализации стенда: требования, воспроизводимые дефекты, тестовые данные, проверочные тесты, оценивание работ и диагностика падений. Студенты получают готовое приложение и занимаются тестированием.

Ограничения первого выпуска:

- Два экрана: вход/регистрация и список заявок. Создание, просмотр, редактирование и комментарии — формы и панель внутри второго экрана.
- Две роли: пользователь и оператор. Оператор создаётся подготовкой данных; самостоятельная регистрация всегда создаёт пользователя.
- Три предметные таблицы: пользователи, заявки, комментарии. Дополнительно одна техническая таблица сессий для отзыва токенов.
- Двенадцать операций основного REST API; технические проверки готовности в это число не входят.
- Три статуса, три значения приоритета, один фильтр по статусу, один фиксированный порядок сортировки.
- Восемь изолированно воспроизводимых дефектов, одинаковых по внешнему проявлению во всех архитектурах.
- В микросервисном варианте — ровно два backend-сервиса.

За границами первого выпуска: вложения, почта, восстановление пароля, отдельная административная панель, назначение исполнителей, уведомления, история действий в интерфейсе, платежи, поиск, пагинация, Redis, очереди, Kubernetes, мобильное приложение. Новая бизнес-функция добавляется только при наличии конкретного учебного задания, которое невозможно выполнить на текущих функциях.

## 2. Стек и недостающие компоненты

| Слой | Решение | Зачем нужен |
|---|---|---|
| Интерфейс | Vue 3, Vite, Tailwind CSS, JavaScript | Два компактных экрана с формами и таблицей |
| Сервер | FastAPI, Pydantic, Uvicorn | REST API, валидация, OpenAPI |
| База данных | PostgreSQL во всех вариантах | SQL, транзакции, ограничения и проверка сохранения данных |
| Доступ к БД | SQLAlchemy, psycopg, Alembic | Небольшие модели и воспроизводимое создание схемы |
| Авторизация | Непрозрачный Bearer-токен, хеш токена в таблице сессий, хеширование паролей Argon2 | Проверки входа, выхода, срока действия и прав без отдельного провайдера идентификации |
| Развёртывание | Docker Compose | Одинаковый запуск на занятиях и в CI |
| Раздача отдельного frontend | Nginx только в двух разделённых вариантах | Статические файлы и маршрутизация `/api` |
| API-автотесты | Python, Pytest, Requests | Соответствие модулю 6 и общий язык автоматизации |
| UI-автотесты | Python, pytest-playwright | Фикстуры, Page Object, ожидания, скриншоты и трассы |
| SQL-проверки | SQL-файлы, psql; psycopg при автоматизации | Практика модуля 7 |
| Ручная проверка API | Postman, экспорт коллекции и окружения | Запросы и проверка ответов без написания полноценного фреймворка |
| Отчёты | JUnit XML, Allure, итог оценивания в JSON и Markdown | Результаты для студента, преподавателя и CI |
| Нагрузка | Один небольшой сценарий Locust | Проверка производительности и поведения при росте нагрузки |

Дополнительные технологии не означают дополнительные постоянно запущенные сервисы. Allure формируется как артефакт; Locust и тестовый контейнер запускаются только для соответствующего задания. Vue Router и Pinia для двух экранов в первом выпуске не требуются. TypeScript можно добавить по предпочтению преподавателя; для целей тестирования он не обязателен.

При реализации выбрать совместимые стабильные версии и зафиксировать зависимости, версии браузеров и образы. Не использовать плавающий `latest` для воспроизводимых учебных запусков. Tailwind подключить через официальный Vite-плагин — [инструкция Tailwind](https://tailwindcss.com/docs/installation/using-vite).

## 3. Шесть веток и смысл архитектур

| Ветка | Развёртывание | Состояние |
|---|---|---|
| `monolith/fixed` | FastAPI отдаёт собранный Vue и API; PostgreSQL отдельно | Исправленная |
| `monolith/buggy` | То же | С учебными дефектами |
| `client-server/fixed` | Отдельный frontend Nginx/Vue, единый FastAPI backend, PostgreSQL | Исправленная |
| `client-server/buggy` | То же | С учебными дефектами |
| `microservices/fixed` | Frontend/Nginx, сервис пользователей, сервис заявок, PostgreSQL | Исправленная |
| `microservices/buggy` | То же | С учебными дефектами |

Монолит и микросервисы также используют клиент-серверное взаимодействие. Эти названия обозначают три учебные схемы размещения и разделения ответственности, а не три взаимоисключающих понятия. В `client-server` backend остаётся монолитным.

Для сохранения Vue во всех ветках `monolith` означает единый артефакт frontend + backend. Это не серверный рендеринг Vue: браузер выполняет собранное приложение. Если потребуется именно серверный HTML-рендеринг как отдельная архитектурная тема, это потребует пересмотра решения; в текущий минимум SSR и Jinja2 не включаются.

В микросервисном варианте:

- Сервис пользователей владеет пользователями и сессиями, выполняет регистрацию, вход и проверку токена.
- Сервис заявок владеет заявками и комментариями; проверяет токен внутренним HTTP-запросом к сервису пользователей с ограниченным временем ожидания.
- Один контейнер PostgreSQL содержит две отдельные базы с отдельными ролями доступа. Сервисы не читают чужую базу и не используют общие ORM-модели данных.
- Внешний `/api` остаётся единым; Nginx маршрутизирует запросы без бизнес-логики.
- При недоступности сервиса пользователей защищённая операция возвращает документированный `503`, а не обходит авторизацию. Это дополнительное упражнение по архитектуре, вне восьми общих дефектов.

Постоянных веток продукта ровно шесть; ветка по умолчанию — `monolith/fixed`. Рабочие ветки студентов находятся в отдельном репозитории работ и не увеличивают число вариантов продукта. Исправленные ветки создаются первыми, дефектные — от соответствующих исправленных коммитов.

Общие требования, UI-контракт, задания и CI-обвязка переносятся между ветками контролируемыми изменениями; отдельная проверка сравнивает их версии. Ветку одной архитектуры целиком в другую не сливать. Перед выдачей курса фиксировать коммиты/образы всех шести вариантов в одном манифесте выпуска, чтобы изменения веток не меняли оценку уже сданной работы.

По умолчанию эталоны открыты: для четырёх студентов это уменьшает обслуживание. Защита ветки от записи не скрывает её содержимое. Если нужны скрытые решения, три исправленных варианта и проверочные материалы следует выдавать из закрытого преподавательского репозитория; это отдельный выбор организации доступа.

## 4. Минимальные правила продукта

Перед кодом оформить небольшой однозначный набор требований с идентификаторами `AUTH-*`, `TICKET-*`, `COMMENT-*`, `UI-*`.

Предлагаемые правила для фиксации в спецификации:

- Регистрация по уникальному нормализованному email и паролю длиной 8–64 символа; повышение роли через входные данные запрещено. Точный порядок нормализации и подсчёта длины описать.
- Вход создаёт сессию; выход отзывает текущую сессию; отсутствующий, неверный, отозванный или истёкший токен даёт `401`.
- У заявки есть идентификатор, автор, заголовок, приоритет, статус и время создания UTC.
- Заголовок после удаления пробелов по краям содержит 3–80 символов. Приоритет принимает только `low`, `normal`, `high`; по умолчанию `normal`.
- Новая заявка имеет статус `new`. Пользователь видит только свои заявки; оператор видит все.
- Автор может менять заголовок и приоритет или удалять заявку только в статусе `new`.
- Статус изменяет оператор: `new → active → closed`, а также `closed → active`. Прямой `new → closed` запрещён. Повторная установка текущего статуса допустима и не меняет другие данные.
- Комментарий имеет автора, заявку, текст 1–300 символов после удаления пробелов по краям и время UTC. Оставлять комментарии могут участники, имеющие доступ к заявке; для `closed` добавление запрещено.
- При удалении заявки удаляются её комментарии; пользовательские аккаунты не удаляются через UI/API.
- Список фильтруется по статусу и сортируется по времени создания, затем по идентификатору для одинакового времени. Комментарии также имеют определённый порядок.
- Чужая недоступная заявка и отсутствующий идентификатор дают `404`. Недостаточная роль для действия над доступной заявкой даёт `403`; запрещённое по состоянию действие — `409`; ошибки входных полей — `422`.
- После успешного изменения UI показывает актуальные данные; текст пользователя отображается текстом и не исполняется как HTML.

Операции API:

| Метод и путь | Назначение |
|---|---|
| `POST /api/auth/register` | Регистрация |
| `POST /api/auth/login` | Вход и получение токена |
| `POST /api/auth/logout` | Выход |
| `GET /api/auth/me` | Текущий пользователь |
| `GET /api/tickets` | Список и фильтрация |
| `POST /api/tickets` | Создание |
| `GET /api/tickets/{id}` | Просмотр |
| `PATCH /api/tickets/{id}` | Изменение заголовка и приоритета |
| `DELETE /api/tickets/{id}` | Удаление |
| `PUT /api/tickets/{id}/status` | Установка статуса |
| `GET /api/tickets/{id}/comments` | Список комментариев |
| `POST /api/tickets/{id}/comments` | Добавление комментария |

Успех создания — `201`, чтения и обновления — `200`, удаления и выхода — `204`; успешный вход — `200`. До реализации определить точные JSON-схемы, заголовки и структуру ошибки. OpenAPI описывает корректное поведение и одинаков в `fixed` и `buggy`: дефекты не должны переписывать требования под ошибочную реализацию.

Одинаковы внешние маршруты, подписи полей, доступные роли элементов и необходимые `data-testid`. API/UI-тесты используют общий `BASE_URL`, а не имена внутренних сервисов.

## 5. База данных и тестовые данные

Таблицы: `users`, `tickets`, `comments`, техническая `sessions`. В единой БД — внешние ключи авторов и заявок, уникальность email и необходимые ограничения. Схема компактная, но содержит записи без комментариев и с несколькими комментариями, разных авторов, статусы и приоритеты.

Основная SQL-практика проводится на `monolith` или `client-server`: доступны `INNER/LEFT/RIGHT JOIN` пользователей, заявок и комментариев, `GROUP BY`, фильтрация, сортировка и проверки целостности. В микросервисах обычного межбазового JOIN и внешнего ключа к пользователю нет; JOIN заявок и комментариев сохраняется, а ссылки на пользователей проверяются через API. Отдельно объяснить это отличие, не добавляя FDW ради упражнения.

Предусмотреть:

- Детерминированные исходные данные: два пользователя, один оператор, несколько заявок каждого статуса, несколько комментариев.
- Отдельную среду Compose для каждого из четырёх студентов; уникальные имена проектов, порты и тома. Для CI — отдельная временная среда на каждый запуск и проверяемый дефект.
- SQL-практику регистрации: подготовка пользователя через `INSERT` с готовым учебным хешем, проверка уникальности, `BEGIN/COMMIT/ROLLBACK`. Открытые пароли в таблицах не хранить.
- Задание «POST через API → SELECT из БД → сверка полей», подготовку данных с `INSERT/UPDATE`, адресную очистку с `DELETE`.
- Уникальные данные теста и фикстуры с очисткой в `finally`. Откат SQL-транзакции теста не считать откатом изменений, выполненных приложением через другое соединение.
- Полный сброс только выделенной учебной среды через служебную команду. Публичный HTTP-метод сброса и доступ студенческих UI/API-тестов к Docker не нужны.

## 6. Каталог учебных дефектов

| Код | Намеренная ошибка | Основной способ проверки |
|---|---|---|
| D01 | API принимает заголовок длиной 81 символ | Граничные значения, API |
| D02 | Недопустимый приоритет молча заменяется на `normal` | Негативный API-тест, проверка отсутствия записи |
| D03 | По прямому идентификатору доступна чужая заявка | Матрица прав, API |
| D04 | Оператор может выполнить `new → closed` | Переходы состояний, API/UI |
| D05 | Фильтр статуса игнорируется | Подготовка разнообразных данных, API/UI |
| D06 | Автором комментария записывается владелец заявки вместо фактического автора | API и SQL; комментарий оператора к чужой заявке |
| D07 | После редактирования приоритета список показывает старое значение до обновления страницы | UI-тест с проверкой результата действия |
| D08 | Текст комментария интерпретируется как HTML | UI, безопасная локальная демонстрация XSS |

Для каждого дефекта преподавательская карточка содержит требование, предусловия, воспроизведение, ожидаемый и фактический результат, уровень проявления и проверочный тест. Точные значения дефектов уточняются после проверки независимости.

В `buggy` поддержать выбор всех дефектов для ручного исследования или одного дефекта для оценивания. Конфигурацию задаёт запускатель; не добавлять в UI переключатель ошибок. UI-дефекты можно выбирать при сборке/запуске соответствующего frontend-артефакта. В `fixed` отсутствует исполняемый механизм включения дефектов.

Каждый одиночный вариант должен запускаться и проходить контроль готовности. Проверить, что D01 и D02 действительно доходят до наблюдаемого поведения, а не перехватываются другим слоем валидации. Режим со всеми дефектами использовать для исследования, но не для вычисления точного покрытия ошибок.

## 7. Два комплекта тестов

Первый комплект принадлежит разработчику стенда и преподавателю:

- Небольшие модульные тесты валидации, правил прав и переходов.
- Проверки реальной PostgreSQL, миграций, связей и удаления комментариев.
- Контрактные API-тесты и несколько UI-сценариев для всех трёх архитектур.
- Контрольные тесты, подтверждающие каждый дефект и отсутствие его в исправленной версии.
- Тесты оценивания на искусственных студенческих работах: корректные тесты, пустой набор, постоянное падение, пропуск проверок, частичное обнаружение дефектов, ошибка настройки и сбой инфраструктуры.

Второй комплект пишут студенты:

- Репозиторий-заготовка содержит зависимости, один нейтральный пример, настройку `BASE_URL`, структуру API/UI-тестов, фикстур и Page Object. Готовые решения заданий не включаются.
- Каждый студент пишет ориентировочно пять содержательных API-тестов и два UI-теста своей области. Число тестов — ориентир нагрузки, а не основной критерий качества.
- В сумме задания охватывают авторизацию, границы полей, роли, статусы, фильтрацию и комментарии. В каждом задании заранее перечислены проверяемые требования и правила начисления баллов.
- Обязательны независимость тестов, управляемые данные, негативный сценарий и параметризация там, где она полезна.
- UI-тесты используют ожидания Playwright и проверки состояния. Проверка только успешного HTTP-ответа не заменяет проверку интерфейса.
- Для переносимых API/UI-тестов доступна только публичная поверхность приложения. SQL-задания модуля 7 выполняются отдельно с учебным доступом к БД.

Playwright предоставляет официальный плагин Pytest, отдельные browser context, выбор браузеров, скриншоты и трассы: [справочник плагина](https://playwright.dev/python/docs/test-runners). Для основного CI достаточно Chromium; Firefox и WebKit запускать в упражнении по совместимости.

## 8. Автоматическая проверка работ

Обычный запуск тестов на дефектном приложении не является достаточной проверкой качества работы. Оценивание использует один и тот же набор студенческих тестов сначала на исправленном приложении, затем на независимых дефектных вариантах.

Последовательность:

1. Взять точный коммит студенческой работы и доверенную версию проверяющего кода; сохранить идентификаторы в отчёте.
2. Убедиться, что тесты обнаружены, задание содержит необходимые API/UI-проверки и разрешённые зависимости.
3. Поднять исправленный вариант, применить миграции, подготовить данные, проверить готовность.
4. Запустить тесты студента на всех трёх исправленных архитектурах. Ошибки и неожиданные пропуски не считать успешным прохождением.
5. Один повторный прогон на свежих данных и с изменённым порядком тестов использовать как ограниченную проверку повторяемости. Это не доказательство отсутствия нестабильности.
6. По одному запускать дефекты, относящиеся к заданию, с новой средой для каждого. Контрольный тест преподавателя подтверждает, что дефект активен.
7. Сопоставить упавшие студенческие проверки с успешным исправленным прогоном и требованием. В зачёт идёт наблюдаемое нарушение контракта, а не любая ошибка процесса.
8. Сформировать итог, сохранить диагностические артефакты и удалить только временные ресурсы этого запуска.

Ошибка сборки, импорта, подготовки данных, тайм-аут ожидания готовности или недоступность runner означают «работа не проверена» либо «ошибка настройки», а не обнаруженный дефект. Не каждый HTTP `500` означает сбой стенда: если запрос к готовому приложению воспроизводимо вызывает нарушение контракта, это может быть результатом дефекта. Причину подтверждают контрольный тест и логи.

Показатель обнаружения: число обнаруженных назначенных дефектов / число назначенных пригодных для проверки дефектов. Для UI-дефектов D07 и D08 нужен UI-тест. Пустой набор, `assert False`, некорректная конфигурация и повсеместные пропуски не получают зачёт. Прохождение исправленных версий — обязательное условие зачёта; штрафы и порог обнаружения фиксируются в задании до выдачи студенту.

Пример: исправленные версии пройдены, обнаружено 3 из 4 назначенных дефектов — 75% обнаружения. Отдельно преподаватель оценивает обоснованность проверок, качество Page Object и фикстур. Автопроверка не заменяет эту часть оценки и не гарантирует защиту от намеренного обхода.

Для быстрой обратной связи в PR/MR: три исправленные архитектуры и назначенные дефекты на основной архитектуре. Полная проверка команды: три архитектуры × (исправленная версия + восемь отдельных дефектов), то есть 27 конфигураций. Полный режим доступен в каждой CI и используется для итогового зачёта; выполнять его по каждому промежуточному коммиту необязательно.

Ожидаемое падение тестов на дефекте не делает весь оценочный pipeline ошибочным. Внешний проверяющий процесс интерпретирует результаты: итоговый статус сообщает, выполнено ли задание, и отдельно отличает ошибку стенда. Прогоны по дефектам не должны прекращаться после первого ожидаемого падения.

## 9. GitHub Actions, GitLab CI и Jenkins

У всех CI одна версия сценария проверки и один формат результата. В репозиториях размещаются тонкие адаптеры `.github/workflows/qa.yml`, `.gitlab-ci.yml` и `Jenkinsfile`. Продуктовые ветки запускают проверку качества самого стенда; PR/MR в репозитории работ запускают оценивание студенческих тестов.

| Система | Событие | Подключение |
|---|---|---|
| GitHub Actions | Создание/обновление PR; ручной полный запуск | Workflow в GitHub-репозитории |
| GitLab CI | Создание/обновление MR; ручной полный запуск | GitLab-репозиторий и правила `merge_request_event` |
| Jenkins | PR/MR через Multibranch Pipeline; ручной запуск | Jenkins, агент, GitHub/GitLab Branch Source, webhook или сканирование |

GitLab MR pipeline по умолчанию проверяет исходную ветку, а GitHub PR workflow обычно использует результат тестового слияния. Для сопоставимости оценивания во всех адаптерах явно выбирать один и тот же коммит студенческой исходной ветки; проверку интеграционного слияния при необходимости выполнять отдельно. События и требования описаны в [GitHub Docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow), [GitLab Docs](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/) и [Jenkins Docs](https://www.jenkins.io/doc/book/pipeline/multibranch/).

Нужны два отдельных размещения Git-репозитория для настоящих GitHub PR и GitLab MR. Зеркалирование коммитов не создаёт PR/MR автоматически. Jenkins подключается к одному или обоим размещениям; отдельная четвёртая площадка хранения исходников не требуется.

Доверенный запускатель управляет Compose, скачивает образы, собирает результат и публикует статус. Код студента запускается отдельно, без секретов площадок, Docker socket, доступа к исходникам проверяющего процесса и его каталогам записи. Правила оценивания берутся из закреплённого преподавательского коммита, а не из изменённого PR/MR. Учебные CI-файлы студент может редактировать по заданию, но они не становятся источником правил итоговой оценки.

Для GitHub использовать `pull_request` для исполнения студенческих тестов; не исполнять их с секретами через `pull_request_target`. Если нужна публикация привилегированного статуса, её делает отдельная доверенная часть после прогона. Это ограничение связано с выполнением внешнего кода, описанным в [руководстве GitHub](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

Проверить три вида демонстрационных работ во всех CI: успешную, не прошедшую задание и не проверенную из-за сбоя среды. Итоговые статусы и обнаруженные дефекты должны совпадать. Перед выпуском каждый из шести вариантов должен пройти соответствующую проверку стенда в каждой системе — 18 комбинаций варианта и CI; для `buggy` успех означает подтверждённые ожидаемые дефекты.

Создание YAML/Jenkinsfile само по себе не означает готовую интеграцию. При приёмке нужны реальные PR, MR, выполненная Jenkins-сборка и опубликованные результаты. Для этого потребуются учётные записи/репозитории, runner GitLab и доступный Jenkins с агентом; место размещения пока не задано.

## 10. Запуск, диагностика и хранение

Каждая ветка запускается одной документированной командой `docker compose up --build`. Обычный запуск приложения не запускает Jenkins и нагрузочные тесты. Сборка Vue выполняется отдельно от runtime; Vite dev server не использовать как сервер учебного готового выпуска.

Готовность включает работающую БД, завершённые миграции и ответ приложения. `depends_on` без проверки готовности недостаточен: [правила запуска Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/). Для ветки с микросервисами проверяется готовность обоих сервисов.

Логи сохраняются в отдельном постоянном каталоге/томе между запусками. В записи: время UTC, уровень, сервис, идентификатор запуска и запроса, HTTP-метод/путь, статус, длительность, идентификаторы сущностей и ошибки с трассой. Один идентификатор запроса передаётся между сервисами. Пароли, токены и полный пользовательский текст не логируются.

Для учебных дефектов нужны логи выполнения операции и отказов, позволяющие связать запрос с обработавшим его компонентом. При анализе ошибки обязательно сопоставлять поведение UI, Network/API, БД и соответствующие записи логов.

Хранение логов и диагностических артефактов — не более 30 дней, с ротацией и очисткой по возрасту. Для локальной среды предусмотреть очистку при запуске и регулярное обслуживание во время работы; для CI — отдельные настройки срока хранения. Сброс тестовой БД не удаляет накопленные логи. Проверить истечение срока хранения на искусственно состаренных файлах и настройки исключений площадок, которые могут сохранять последние артефакты дольше установленного срока.

При падении UI-теста сохранять скриншот, Playwright trace, консоль браузера и относящиеся к запросу серверные логи. Для API — обезличенные запрос/ответ и идентификатор запроса. Отчёт включает версии приложения, проверяющего кода и тестов.

Все инструкции, комментарии, учебные материалы и описания коммитов — на русском. При создании репозитория включить в `.gitignore` локальные инструкции для ИИ, включая `AGENTS.md`, секреты, окружения, кэши, результаты сборок, логи и генерируемые отчёты. Человеческую документацию курса хранить в Git. Обратную совместимость с прошлыми версиями задания не поддерживать; выпуск курса закреплять версиями.

Большие загрузки Docker-образов и браузеров оформить отдельным PowerShell-скриптом предварительной подготовки для самостоятельного запуска пользователем. В текущем планировании ничего не скачивать и не устанавливать.

## 11. Учебные материалы и связь с программой

| Модуль | Практика на минимальном стенде | Результат |
|---|---|---|
| 1 | Три схемы архитектуры, путь запроса, роль тестирования в pipeline | Схема и краткий план работы команды |
| 2 | Длины полей, роли, приоритеты, статусы; pairwise роли/статуса/приоритета с учётом недопустимых сочетаний | Границы, классы эквивалентности, таблица решений, переходы, попарный набор |
| 3 | Небольшая учебная копия требований с 3–4 противоречиями или пробелами | Замечания; затем выдача согласованного контракта |
| 4 | Проверки тех же двух экранов и API, баги с доказательствами | Тест-план, кейсы, баг-репорты, отчёт и покрытие требований |
| 5 | Исследовательская сессия, доступ к чужой заявке, ввод SQL/XSS-строк, рост нагрузки, другие браузеры и клавиатура | Отчёт о рисках, результаты нагрузки и совместимости |
| 6 | Двенадцать операций API, ошибки, токены, DevTools и прокси | Postman-коллекция, несколько Requests-тестов, диагностика по логам |
| 7 | Реальная PostgreSQL, JOIN, DML, транзакции и проверка POST в БД | SQL-подготовка, проверки и адресная очистка |
| 8 | Pytest, Requests, Playwright, Page Object, фикстуры, параметризация и CI | PR/MR с автоматически проверенными API/UI-тестами |
| 9 | Зафиксированный релиз-кандидат с выбранным набором дефектов | Регрессия, отчёт, обоснованное решение о релизе |

Встроенная аутентификация — Bearer-сессии, а не полноценный OAuth 2.0 сервер. Для терминов Basic Auth, OAuth 2.0 и JSON/XML подготовить короткие дополнительные упражнения на готовых HTTP-примерах/локальных заглушках вне бизнес-функций: Basic-заголовок, последовательность Authorization Code с PKCE, ответы токенного обмена, `401/403`, разбор XML. Если требуется реальная интеграция с OAuth-провайдером, это отдельное расширение, которое нужно согласовать. Не называть обычный `/login` реализацией OAuth 2.0.

Для SQL Injection необязательно закладывать реальную уязвимость: проверка корректной обработки опасных строк и параметризованных запросов также полезна. XSS-демонстрация D08 проводится только на локальной учебной среде. Нагрузочное упражнение использует ограниченные ресурсы и ступенчатый рост нагрузки; показатели интерпретируются относительно описанной среды, а не как универсальная характеристика продукта.

Разделение четырёх студентов: авторизация/доступ; поля/редактирование; статусы/фильтр; комментарии/отображение. У всех есть UI, API и SQL-практика. Индивидуально оцениваются назначенные требования и дефекты, а объединённый комплект покрывает весь продукт. Для итоговой работы достаточно нового сочетания дефектов или зафиксированного исправления; новые бизнес-функции и седьмая постоянная ветка не требуются.

## 12. Последовательность реализации и критерии приёмки

| Этап | Что реализовать | Проверяемый результат |
|---|---|---|
| 1. Контракт | Минимальные требования, таблица ролей/статусов, API-схемы, модель БД, список восьми дефектов и критерии заданий | Каждое правило проверяемо; каждая функция связана с учебной задачей |
| 2. Исправленный монолит | Два экрана, API, PostgreSQL, миграции, исходные данные, Docker и постоянные логи | Полный сценарий создания/обработки/комментария проходит через UI и подтверждается API/БД |
| 3. Проверки стенда | Модульные, интеграционные, API и минимальные UI-тесты преподавателя | Исправленный вариант проходит проверки с чистой БД и после перезапуска |
| 4. Пробное оценивание | Дефектная пара монолита, сначала один API-дефект и один UI-дефект, внешний проверяющий процесс | Хороший тест проходит эталон и обнаруживает дефект; постоянное падение и пустой набор не засчитываются |
| 5. Полный каталог | Все восемь дефектов и их контрольные тесты | Каждый включается отдельно и воспроизводится; общий режим пригоден для ручного исследования |
| 6. Остальные архитектуры | Разделённый frontend и два backend-сервиса, исправленная/дефектная пара каждого | Созданы шесть веток; общий API/UI-набор работает на трёх исправленных вариантах |
| 7. CI | Единый запускатель, три адаптера, публикация результатов, изоляция и очистка | Настоящие PR/MR и Jenkins дают сопоставимые статусы для трёх демонстрационных работ |
| 8. Материалы | Заготовка тестового репозитория, Postman, SQL-задания, шаблоны документации, Locust, инструкция подготовки | Студент может выполнить задания без разработки приложения |
| 9. Репетиция курса | Четыре отдельные среды, полный прогон матрицы, повторные запуски, проверка логов и сроков хранения | Среды не мешают друг другу; результаты воспроизводимы; выпуск зафиксирован |

Оценщик проверяется уже на монолите, до размножения реализации на три архитектуры. Это позволяет рано подтвердить главный учебный механизм и скорректировать устройство дефектов без синхронизации шести веток.

Итоговая приёмка требует демонстрации: запуска каждой ветки; прохождения эталонных тестов на исправленных версиях; подтверждения восьми дефектов; проверки студенческого PR/MR; SQL-проверки сохранённой записи; диагностики одного падения по сквозному идентификатору запроса; сохранения логов после перезапуска; независимости четырёх сред.

## 13. Решения, которые можно скорректировать

Уже зафиксированы пользователем: стек Vite/Vue 3/FastAPI/Tailwind/Docker, PostgreSQL, шесть веток, три CI и приоритет тестирования при минимальном приложении.

Рабочие допущения этого плана: предметная область «Мини-заявки»; JavaScript; открытые исправленные ветки; отдельный репозиторий студенческих работ; Python-автоматизация; два микросервиса; один PostgreSQL-контейнер с двумя базами в микросервисах; основной прогон Chromium.

До подключения внешних CI потребуется определить площадки GitHub/GitLab, доступный Jenkins/runner, где студенты запускают Docker и нужно ли скрывать эталоны. Эти сведения не мешают разработке локального стенда и проверяющего процесса, но нужны для завершения интеграционной приёмки.
